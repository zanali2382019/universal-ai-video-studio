## 2. القرارات المعمارية النهائية للنقاط الثلاث الأخيرة

### 1. التعافي الآمن للأصول وخطة العزل دون حذف الأصول السليمة (Safe Recovery of Original Assets)
- **الملاحظة:** حظر حذف أي ملف من `media_vault/originals/` لمجرد اختلاف بصمة التجزئة SHA-256، والتحقق الصارم من ملكية الملف وربطه بسجل `file_operations` و `media_assets` والمراجع النشطة، ونقل الملفات المشبوهة أو المتضاربة إلى مسار العزل الآمن (`quarantine/`) دون حذف أصل سليم.
- **القرار المعماري النهائي:**
  1. **حظر الحذف المباشر في `originals/`:** يُمنع منعاً باتاً حذف أي ملف موجود داخل `media_vault/originals/` لمجرد عدم تطابق بصمة SHA-256 مع العملية الحالية؛ فالملف قد يكون أصلاً معتمداً لقناة أو مشهد آخر تم إنشاؤه مسبقاً.
  2. **التسجيل المسبق للبصمة المتوقعة (Pre-Replace Commitment):** قبل استدعاء `os.replace`، يُلزم العامل بتسجيل بصمة SHA-256 المحسوبة للملف المؤقت في جدول `file_operations` بحالة `FILE_WRITTEN`، برقم عملية حتمي:  
     `file_op_id = "op_" + task_id + "_" + step_name + "_tok" + execution_token`.
  3. **مسار العزل الآمن (`quarantine/`):** إذا وُجد ملف في مسار الهدف المتوقع ولكن بصمته اختلفت عن المتوقع ولا يوجد له سجل مالك في `media_assets`، يتم نقله فوراً إلى:  
     `channels/{ch}/media_vault/quarantine/{filename}.quarantine_{timestamp}`  
     مع تسجيل تحذير حرج في سجل التدقيق، وتحويل العملية إلى `FAILED` بسبب خطأ نزاهة (**Integrity Error**)، مما يضمن عدم تدمير ملفات غير معروفة وبدء الخطوة بنظافة.
  4. **حماية الأصول القائمة من التضارب:** إذا كان الملف في `originals/` مسجلاً بالفعل لأصل آخر في `media_assets` وبصمته مختلفة، يُمنع لمسه وتفشل العملية بـ `AssetPathCollisionException`. وإذا تطابقت بصمته مع المهمة الحالية، يتم اعتماده فوراً بنمط إعادة استخدام التخزين (Deduplication Reuse).
- **القيود:** ذرية العمليات تعتمد على نزاهة نظام الملفات المحلي (NTFS/POSIX).

### 2. الدلالات الكاملة لترويسة `Retry-After` وفحص TTL الشامل (Complete Retry-After Semantics)
- **الملاحظة:** دعم صيغتي الثواني (Delta-seconds) وتاريخ HTTP (HTTP-date)، ومعالجة انحراف الساعة (Clock Skew) والتواريخ غير الصالحة، وحظر إعادة الإرسال قبل موعد المزود، وتطبيق فحص مهلة الصلاحية القصوى للمهمة (Task TTL = 24h) على كافة أنواع التأخير.
- **القرار المعماري النهائي:**
  1. **دعم الصيغتين المعياريتين (RFC 7231 / RFC 9110):** دعم صيغة الثواني الرقمية `Retry-After: 120` وصيغة التاريخ الرسمي `Retry-After: Wed, 21 Oct 2026 07:28:00 GMT`.
  2. **معالجة انحراف الساعة والتواريخ غير الصالحة:**
     - تحليل التاريخ كطابع زمني UTC موحد.
     - في حال فشل التحليل، يسقط النظام تلقائياً لمعادلة التراجع الأسي الداخلية مع تسجيل تحذير.
     - احتساب الفارق الزمني: $\Delta t = (T_{\text{http\_date}} - T_{\text{now\_utc}}).\text{total\_seconds}()$.
     - إذا كانت $\Delta t \le 0$ (ساعة المزود متأخرة أو الوقت انقضى): يُحظر الإرسال الفوري عند الصفر، ويتم تطبيق مهلة أمان تشويشية: $\text{EffectiveDelay} = \text{uniform}(3, 7)\text{s}$.
     - إذا كانت $\Delta t > 0$: $\text{EffectiveDelay} = \Delta t$.
  3. **فحص مهلة الصلاحية القصوى الشامل (Universal TTL Gate):**
     - كل تأخير مجدول (داخلي أو من المزود) يخضع لشرط: $\text{ScheduledTime} = \text{now} + \text{EffectiveDelay}$.
     - إذا كانت $\text{ScheduledTime} > \text{created\_at} + 24\text{h}$ (TaskTTL): تتحول المهمة فوراً ودون أي انتظار إلى **`FAILED`** بسبب تجاوز مهلة الصلاحية (`RateLimitExceedsTaskTTL`)، وتُلغى كافة المهام التابعة.
  4. **حظر الإرسال المبكر نهائياً:** يُحظر على النظام إرسال أي طلب قبل حلول الطابع الزمني الصريح للمزود.

### 3. دورة حياة حيازة القناة الذرية في SQLite وضمانات Fencing Token
- **الملاحظة:** تحديد متى تُحرر الحيازة بدقة، وضمان عدم مساس `TaskReaper` بحيازة عامل أحدث، واشتراط مطابقة المفاتيح الأربعة عند التجديد أو التحرير، وتوثيق سيناريو انتهاء الحيازة وصد Fencing Token، وضمان الذرية في SQLite.
- **القرار المعماري النهائي:**
  1. **قواعد تحرير الحيازة:** تُحجز الحيازة في `active_channel_leases` **حصراً أثناء حالة `RUNNING`**. وتُحذف الحيازة وجوباً عند الانتقال لأي حالة أخرى:  
     `RETRY_PENDING`، `RETRY_PENDING_APPROVAL`، `FAILED`، `CANCELLED`، `COMPLETED`.
  2. **قيد المطابقة الرباعي الإلزامي:**
     لا يتم تجديد أي حيازة (في نبض الحياة) ولا تحريرها (عند الانتهاء أو الاسترداد) إلا بمطابقة المفاتيح الأربعة معاً:
     $$\text{MATCH KEYS: } (\text{channel\_id}, \text{task\_id}, \text{worker\_id}, \text{execution\_token})$$
  3. **حصانة حيازة العامل الجديد ضد `TaskReaper`:**
     عند استرداد مهمة منتهية الحيازة، ينفذ المسترد حذف الحيازة بشرط مطابقة `worker_id` و `execution_token` القديمين؛ فإذا كان عامل أحدث قد استلم المهمة برمز أعلى، سيعيد أمر الحذف `rowcount == 0`، مما يمنع المسترد قطعياً من المساس بحيازة العامل الجديد.
  4. **سيناريو صد العامل القديم (Fencing Token Defense):**
     إذا استيقظ عامل قديم بعد انتهاء حيازته وقيام عامل جديد باستلام المهمة:
     - نبض الحياة: يفشل (`rowcount == 0`).
     - كتابة Checkpoint أو إكمال المهمة: يفشل (`rowcount == 0`) لاختلاف الرمز.
     - يتلقى العامل القديم `StaleExecutionTokenException`، فيحذف ملفاته المؤقتة الخاصة برمز جلسته فقط، ولا يمس ملفات العامل الجديد، ويموت بأمان دون تلويث قاعدة البيانات.
  5. **الذرية التامة للمعاملات في SQLite:**
     كافة عمليات سحب المهام وحجز الحيازات وتغيير الحالات تُنفذ دوماً داخل معاملات SQLite فورية `BEGIN IMMEDIATE` لضمان عدم وجود أي حالة وسيطة غير متسقة عبر كافة العمليات والخيوط المتزامنة.
