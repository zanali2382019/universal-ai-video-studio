## 1. الخلفية والأهداف الهندسية (Context & Objectives)

تحدد هذه الوثيقة المعايير المعمارية الحاكمة لتنفيذ المهمة 3.4 وما بعدها، وتعالج بدقة هندسية عالية النقاط التالية:
1. **مصدر الحقيقة الأحادي (Single Source of Truth - SSOT):** ترسيخ SQLite كمصدر وحيد للحقيقة للبيانات التشغيلية، وإلغاء أي ملفات JSON موازية.
2. **يومية التعافي من الانهيار (Crash Recovery Journal):** تصميم جدول دائم `file_operations` لإدارة دورة حياة الملفات واستعادة الاتساق بعد الانقطاع المفاجئ دون فقدان البيانات.
3. **سلامة وتزامن سجل التدقيق بنمط Transactional Outbox:** معالجة دقيقة وشاملة لجميع سيناريوهات الانقطاع بين SQLite وملف التدقيق، وإدارة التزامن عبر العمليات المتعددة، والتحقق الصارم من البادئة عند التعافي من الكتابة الجزئية.
4. **ضمانات بيئة Windows و NTFS:** توثيق حدود ما تضمنه وما لا تضمنه نداءات `flush()` و `FlushFileBuffers` (os.fsync) والتعامل مع إنشاء الملفات والمجلدات.
5. **منع ازدواجية تخزين الأصول:** تخصيص مستودع مركزي وحيد للأصول الثنائية، وجعل مجلدات الشخصيات والعلامة التجارية مراجع منطقية.
6. **التمييز الصارم لسياسات الحذف:** الفصل بين (Disable، Archive، Remove Association، Purge) وحماية أدلة التراخيص وسجلات التدقيق من الحذف إطلاقاً.
7. **فصل السجلات التشغيلية:** التمييز الصارم بين سجلات التطبيق التشخيصية وسجلات تدقيق العمليات وسجلات التراخيص.
8. **مصفوفة اختبارات نظرية شاملة:** تغطي كافة سيناريوهات الانقطاع، والتزامن، والتكرار، والتلاعب.

## 2. مصدر الحقيقة الأحادي للبيانات (Single Source of Truth - SSOT)

> [!IMPORTANT]
> **قاعدة معمارية قطعية: SQLite هي المصدر الحصري للحقيقة لجميع البيانات المنظمة والعلاقات التشغيلية.**  
> يُحظر تماماً إنشاء ملفات JSON موازية تعمل كمخازن حية للبيانات أو كـ Manifests تشغيلية قد تتعارض مع قاعدة البيانات.

### 2.1. مصفوفة توزيع المسؤوليات بين SQLite ونظام الملفات:

| فئة البيانات | مكان التخزين المعتمد | مصدر الحقيقة (SSOT) | طبيعة دور نظام الملفات |
| :--- | :--- | :--- | :--- |
| **القنوات والإعدادات والهوية** | جدول `channels` في SQLite | **SQLite** | لا يوجد ملف حي؛ يُولد `channel_profile.json` كحزمة تصدير عند الطلب الصريح فقط. |
| **المشاريع وحالاتها ومواصفاتها** | جدول `projects` في SQLite | **SQLite** | أُلغي ملف `project.json` التشغيلي تماماً؛ الملفات على القرص هي كاش ومخرجات مرحلية. |
| **المشاهد والنصوص والترتيب** | جدول `scenes` في SQLite | **SQLite** | نصوص المشاهد، التوقيت، الترتيب، والمتغيرات مخزنة حصراً في قاعدة البيانات. |
| **الأصول الرقمية والخصائص** | جدول `media_assets` في SQLite | **SQLite** | نظام الملفات يحفظ **الملف الثنائي فقط (Binary Payload)**، وتجزئة SHA-256 والمسار مسجلة في DB. |
| **التراخيص والأساس القانوني** | جدول `asset_licenses` في SQLite | **SQLite** | نظام الملفات يحفظ **وثائق الإثبات المادية (PDF، فواتير، صور)**؛ أُلغي `licenses_registry.json`. |
| **بيانات الشخصيات ومواصفاتها** | جدول `characters` في SQLite | **SQLite** | أُلغي `character_manifest.json` كملف حي؛ مواصفات ومراجع الشخصية تُسجل في قاعدة البيانات. |
| **تعريفات القوالب التشغيلية** | جدول `templates` في SQLite | **SQLite** | قوالب المحرك المشتركة تُقرأ كنواة كودية؛ قوالب القناة المخصصة تُسجل في قاعدة البيانات. |
| **يومية عمليات الملفات** | جدول `file_operations` في SQLite | **SQLite** | تتبع الحالات المرحلية للملفات لضمان التعافي التام عند انقطاع الطاقة. |
| **صندوق حركات التدقيق** | جدول `audit_events_outbox` في SQLite | **SQLite** | تسجيل حركات التدقيق ضمن المعاملة الذرية ذاتها قبل تفريغها للملف. |
| **حالة تدقيق التراخيص** | جدول `audit_chain_state` + ملف `audit/license_audit.log` | **SQLite + Append Log** | السجل الإلحاقي النصي بصيغة JSONL للتدقيق، وآخر تجزئة موثوقة في SQLite. |

## 3. يومية التعافي من الانهيار والعمليات الذرية للملفات (Crash Recovery Journal)

لمنع أي تباين بين SQLite ونظام الملفات عند توقف التطبيق فجأة أو انقطاع التيار أثناء كتابة ملف، يتم تطبيق **نمط اليومية الدائمة (Persistent Journaling Pattern)** عبر جدول `file_operations`.

### 3.1. هيكل جدول `file_operations` في SQLite:
```sql
CREATE TABLE file_operations (
    id TEXT PRIMARY KEY,                       -- UUID فريد للحركة
    operation_type TEXT NOT NULL,              -- IMPORT, RENDER, EXPORT, PURGE
    channel_id TEXT NOT NULL REFERENCES channels(id),
    asset_id TEXT,                             -- معرف الأصل المرتبط إن وجد
    source_path TEXT,                          -- مسار الملف المصدر
    temp_path TEXT NOT NULL,                   -- مسار الملف المؤقت (.tmp.<uuid>)
    target_path TEXT NOT NULL,                 -- المسار النهائي المستهدف
    file_sha256 TEXT,                          -- تجزئة المحتوى
    file_size_bytes INTEGER,                   -- حجم الملف بالبايت
    state TEXT NOT NULL,                       -- PENDING, FILE_WRITTEN, DB_COMMITTED, FILE_FINALIZED, COMPLETED, FAILED
    error_message TEXT,                        -- تفاصيل الخطأ عند الفشل
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
CREATE INDEX idx_file_ops_state ON file_operations(state);
CREATE INDEX idx_file_ops_channel ON file_operations(channel_id);
```

### 3.2. دورة حياة العملية وترتيب الخطوات (Execution Sequence):

```text
 [1. PENDING] ──────────► تسجيل نية العملية في file_operations
       │
       ▼
 [2. FILE_WRITTEN] ─────► كتابة البايتات في المسار المؤقت (.tmp.<uuid>) + التحقق من الحجم و SHA-256
       │
       ▼
 [3. DB_COMMITTED] ─────► فتح معاملة SQLite: إدراج سجل الأصل (media_assets) وتحديث حالة اليومية
       │
       ▼
 [4. FILE_FINALIZED] ───► نقل/إعادة تسمية ذرية (Atomic Rename) من .tmp.<uuid> إلى target_path
       │
       ▼
 [5. COMPLETED] ────────► تمكين الأصل للاستخدام وإنهاء قيد اليومية بنجاح
```

### 3.3. مصفوفة الاستعادة عند الانهيار (Crash Recovery Matrix):

عند تشغيل التطبيق أو تهيئة سياق القناة، يُنفذ **بروتوكول المصالحة (Reconciliation Protocol)** بفحص قيود `file_operations` غير المكتملة:

| حالة القيد عند الانهيار | الحالة المادية على القرص | إجراء الاستعادة التلقائي (Recovery Action) | النتيجة النهائية |
| :--- | :--- | :--- | :--- |
| **`PENDING`** | الملف المؤقت إما غير موجود أو غير مكتمل | حذف أي ملف مؤقت موجود يحمل نفس الـ UUID، وتحديث القيد إلى `FAILED`. | لا يوجد أصل في DB ولا مخلفات على القرص. |
| **`FILE_WRITTEN`** | الملف المؤقت موجود ومكتمل البايتات، لكن معاملة DB لم تتم | حذف الملف المؤقت `.tmp.<uuid>` وتحديث القيد إلى `FAILED`. | حماية قاعدة البيانات من أي إدخال معلق، وعدم ترك ملف يتيم. |
| **`DB_COMMITTED`** | معاملة DB اكتملت، والملف لا يزال بالمسار المؤقت `.tmp.<uuid>` | **إكمال النقل الذري فوراً** إلى `target_path`، وتحديث القيد إلى `FILE_FINALIZED` ثم `COMPLETED`. | **عدم فقدان أي بيانات** واستعادة التوافق الكامل بين DB والقرص. |
| **`FILE_FINALIZED`** | الملف في مساره النهائي بنجاح، ولم يُحدث القيد إلى مكتمل | تحديث القيد فوراً إلى `COMPLETED`. | اكتمال السجل بنجاح. |

## 4. حماية وتزامن سجل التدقيق بنمط (Transactional Outbox Pattern)

### 4.1. هيكل جدول `audit_events_outbox`:
```sql
CREATE TABLE audit_events_outbox (
    seq INTEGER NOT NULL,                      -- رقم تسلسلي متزايد محكوم بقفل SQLite
    idempotency_key TEXT NOT NULL,             -- مفتاح حتمية يمنع التكرار
    channel_id TEXT NOT NULL REFERENCES channels(id),
    payload_json TEXT NOT NULL,                -- النص القياسي للحركة (Canonical JSON)
    previous_hash TEXT NOT NULL,               -- تجزئة السطر السابق
    entry_hash TEXT NOT NULL,                  -- تجزئة السطر الحالي
    file_flushed INTEGER DEFAULT 0,            -- 0 = معتمد في DB ولم يفرغ في الملف، 1 = مفرغ ومؤكد بـ fsync
    created_at TEXT NOT NULL,
    PRIMARY KEY (channel_id, seq),
    UNIQUE (channel_id, idempotency_key)
);
CREATE INDEX idx_outbox_unflushed ON audit_events_outbox(channel_id, file_flushed) WHERE file_flushed = 0;
```

### 4.2. دورة حياة حركة التدقيق المعيارية:

```text
 ┌────────────────────────────────────────────────────────────────────────────────────────┐
 │ المرحلة الأولى: المعاملة الذرية في SQLite (Atomic Transaction Phase)                     │
 ├────────────────────────────────────────────────────────────────────────────────────────┤
 │ 1. فتح معاملة SQLite فورية: BEGIN IMMEDIATE                                            │
 │ 2. تنفيذ العملية الأساسية (مثل اعتماد ترخيص أصل في asset_licenses)                     │
 │ 3. قراءة last_seq و latest_audit_hash من جدول audit_chain_state للقناة                 │
 │ 4. حساب:                                                                               │
 │    seq = last_seq + 1                                                                  │
 │    entry_hash = SHA256(latest_audit_hash + canonical_json(payload))                    │
 │ 5. إدراج الحركة في جدول audit_events_outbox بقيمة (file_flushed = 0)                   │
 │ 6. تحديث جدول audit_chain_state بقيم seq و entry_hash الجديدة                          │
 │ 7. اعتماد المعاملة بالكامل: COMMIT SQLite                                              │
 └────────────────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼ (المعاملة اعتمدت ذرياً في SQLite)
 ┌────────────────────────────────────────────────────────────────────────────────────────┐
 │ المرحلة الثانية: التفريغ الفيزيائي في ملف السجل (Flush & Fsync Phase)                   │
 ├────────────────────────────────────────────────────────────────────────────────────────┤
 │ 8. حجز قفل القناة الإجرائي عبر العمليات (Cross-Process Channel Mutex)                   │
 │ 9. التحقق من مطابقة نهاية الملف: seq(tail) == seq(next) - 1                            │
 │ 10. كتابة السطر النصي الكامل المنتهي بـ Newline (\n)                                   │
 │ 11. تفريغ وتثبيت البايتات فيزيائياً: file.flush() ثم os.fsync(fd)                      │
 │ 12. تحديث جدول audit_events_outbox بجعل file_flushed = 1 لحركة seq المعنية           │
 └────────────────────────────────────────────────────────────────────────────────────────┘
```

## 5. معالجة الحالات التشغيلية الحرجة الأربع (Detailed Operational Resolution)

### الحالة الأولى: الانقطاع بعد كتابة السطر و fsync() وقبل تحديث file_flushed في SQLite

* **وصف الحالة:** كُتب السطر $N$ كاملاً ومطابقاً في `license_audit.log` وثُبّت بـ `os.fsync()`، لكن التطبيق تعطل قبل تنفيذ تحديث `file_flushed = 1` في SQLite. عند بدء التشغيل: قاعدة البيانات تُظهر `file_flushed = 0` للقيد $N$، بينما الملف يحتوي على السطر $N$ بالفعل.
* **آلية الاكتشاف الدقيقة:**
  1. عند تشغيل بروتوكول المصالحة وتفريغ الـ Outbox، يُستخرج القيد المعلّق $N$ (`file_flushed = 0`).
  2. يُفحص آخر سطر صالح في نهاية ملف `license_audit.log`.
  3. يكتشف النظام أن رقم التسلسل للسطر الأخير في الملف يساوي تماماً $N$ (`tail_seq == N`).
  4. يُحلل سطر الملف ككائن JSON وتتم مطابقته مع قيد الـ Outbox:
     - تطابق `seq == N`.
     - تطابق `idempotency_key == outbox.idempotency_key`.
     - تطابق `previous_hash == outbox.previous_hash`.
     - تطابق `entry_hash == outbox.entry_hash`.
     - تطابق المحتوى `canonical_json(payload) == outbox.payload_json`.
* **المعالجة الآمنة:**
  - **إذا تطابقت الحقول بالكامل (100% Match):**
    - يثبت يقيناً أن السطر كُتب وثُبّت بنجاح كامل قبل الانقطاع وأن التحديث فقط هو ما فات.
    - **يُمنع منعاً باتاً إعادة كتابة السطر في الملف** (لمنع تكرار السجلات أو كسر السلسلة).
    - تُفتح معاملة في SQLite وتُنفذ:
      `UPDATE audit_events_outbox SET file_flushed = 1 WHERE channel_id = ? AND seq = ?;`
    - تستمر دورة العمل الطبيعية دون إغلاق بوابة التصدير.
  - **إذا وُجد أي اختلاف بين سطر الملف وقيد الـ Outbox (Hash Mismatch أو Payload Conflict):**
    - هذا ليس مجرد انقطاع في التحديث، بل تضارب بيانات أو تلاعب.
    - يُرمى فوراً استثناء `AuditIntegrityException` وتُقفل بوابة التصدير (`Export Gate Hard Lock`).

---

### الحالة الثانية: التزامن وترتيب الكتابة عبر العمليات المتعددة (Multi-Process Single-Writer Guarantee)

* **وصف المشكلة:** تشغيل عدة عمليات متزامنة للمنصة (مثل CLI worker + عملية رندر خلفية + واجهة GUI) تحاول تفريغ أحداث الـ Outbox لنفس القناة، مما قد يسبب تداخلاً في أسطر الملف أو كتابة أحداث بترتيب غير صحيح.
* **آلية المعالجة والضمانات المعمارية:**
  1. **حجز كاتب واحد حصري لكل قناة (Per-Channel Single Writer Lock):**
     - يُنشأ قفل ملف إجرائي على مستوى نظام التشغيل: `channels/<channel_id>/audit/.audit_lock`.
     - على بيئة **Windows**: يُستخدم قفل المقاطع الإلزامي عبر Win32 API (`msvcrt.locking` مع `LK_NBLCK` أو `LockFileEx`).
     - يمنع هذا القفل أي عملية أخرى من محاولة تفريغ الـ Outbox لنفس القناة في نفس اللحظة.
  2. **ترتيب صارم للأحداث المسترجعة (Strict Sequential Ordering):**
     - استعلام استخراج الأحداث المعلّقة يُلزم بالترتيب التسلسلي المتزايد حصراً:
       `SELECT * FROM audit_events_outbox WHERE channel_id = ? AND file_flushed = 0 ORDER BY seq ASC;`
  3. **التحقق من اتصال السلسلة قبل كل عملية إلحاق (Chain Continuity Check):**
     - قبل إلحاق الحدث $N$ بالملف، تقرأ العملية آخر سطر في الملف وتتحقق من شرطين رياضيين حاسمين:
       $$\text{file\_tail.seq} == N - 1$$
       $$\text{file\_tail.entry\_hash} == \text{event}[N].\text{previous\_hash}$$
     - إذا لم يتحقق الشرط (مثلاً لو كان الملف عند $N-2$ أو حدث قفز في الترتيب): تتوقف العملية فوراً، ولا يُكتب أي بايت في الملف، وتُعلن حالة `Integrity Failure` لمنع كسر السلسلة.

---

### الحالة الثالثة: التعافي من الكتابة الجزئية (Torn Write) بشرط البادئة الصارم (Strict Prefix Match Rule)

* **القاعدة الأمنية الحاكمة:** **لا يُسمح باقتطاع أي بيانات من نهاية الملف لمجرد أنها بايتات غير مكتملة أو مجهولة. لا يُسمح بالاقتطاع إلا بإثبات رياضي قاطع بأن البايتات المشوهة هي بادئة مطابقة تماماً للسطر المتوقع من حدث Outbox معتمد.**
* **آلية الاكتشاف والفحص:**
  1. يقرأ بروتوكول المصالحة نهاية ملف `license_audit.log`.
  2. إذا انتهى الملف ببايتات $B_{\text{tail}}$ لا تنتهي برمز السطر الجديد (`\n`) أو لا تمثل كائن JSON مكتمل وصالح:
     - يتم تحديد موقع نهاية آخر سطر مكتمل وصحيح $N-1$ مع معرفة إزاحته الفيزيائية بالبايت في الملف ($Offset_{N-1}$).
     - يتم استخراج الحدث المتوقع $N$ من جدول `audit_events_outbox` في SQLite الذي يحمل `seq = N` و `file_flushed = 0`.
     - يتم تشكيل البايتات المتوقعة الكاملة لهذا السطر:  
       $$B_{\text{expected}} = (\text{canonical\_json}(event_N) + \text{"\textbackslash n"}).\text{encode}('utf-8')$$
     - يُجري النظام فحص البادئة الثنائية:
       $$\text{is\_valid\_torn\_write} = B_{\text{expected}}.\text{startswith}(B_{\text{tail}}) \quad \mathbf{AND} \quad \text{len}(B_{\text{tail}}) < \text{len}(B_{\text{expected}})$$
* **المعالجة والقرار:**
  - **إذا تحقق شرط البادئة الصارم ($\text{is\_valid\_torn\_write} == \text{True}$):**
    - ثبت يقيناً أن البايتات المشوهة هي نتاج انقطاع الطاقة أثناء كتابة الحدث المعتمد $N$.
    - يُقتطع الملف بدقة متناهية إلى إزاحة السطر السابق: `file.truncate(Offset_{N-1})`.
    - يُعاد كتابة السطر المتوقع كاملاً $B_{\text{expected}}$ من البداية.
    - يُنفذ `file.flush()` متبوعة بـ `os.fsync(fd)`.
    - يُحدث سجل الـ Outbox إلى `file_flushed = 1`.
  - **إذا فشل شرط البادئة ($\text{is\_valid\_torn\_write} == \text{False}$ أو لم يوجد حدث معلّق $N$):**
    - البايتات الموجودة في نهاية الملف غريبة، أو محقونة يدوياً، أو نتجت عن تلف وسيط التخزين.
    - **يُحظر الاقتطاع قطعياً (Prohibit Truncation).**
    - يُرمى استثناء `AuditIntegrityException` فوراً وتُقفل بوابة التصدير (`Export Gate Hard Lock`).

---

### الحالة الرابعة: الضمانات والحدود الواقعية لبيئة Windows ونظام NTFS

* **ما تضمنه وما لا تضمنه عمليات الإفراغ والتثبيت:**
  1. **استدعاء `file.flush()` في بايثون:**
     - **يضمن:** تفريغ بافر C-Runtime ومستوى المستخدم في بايثون إلى ذاكرة كاش نظام تشغيل Windows.
     - **لا يضمن:** كتابة البيانات على أقراص التخزين المادية (Data can still be lost on sudden power loss).
  2. **استدعاء `os.fsync(fd)` على Windows:**
     - يُترجم في نواة بايثون لويندوز إلى نداء الـ Win32 API:  
       `FlushFileBuffers(HANDLE)`
     - **ما يضمنه على NTFS:**
       - إجبار نظام التخزين على إفراغ صفحات الكاش المعدلة للملف إلى وحدة التخزين المادية.
       - تحديث بيانات الملف الوصفية وحجمه وتوقيته في سجلات جدول الملفات الرئيسي (`$MFT`) وتثبيتها في دفتر أستاذ NTFS التبادلي (`$LogFile`).
     - **ما لا يضمنه (حدود عتادية ونظامية):**
       - **كاش وسائط التخزين الاستهلاكية (Drive Controller Write Cache):** بعض أقراص SSD/HDD الاستهلاكية تُخطر نظام التشغيل باكتمال الكتابة بينما تكون البيانات لا تزال في الـ DRAM Controller الداخلي للقرص، وتفقد البيانات إذا انقطعت الطاقة دون وجود مكثفات حماية (Power-Loss Protection - PLP).
       - **أقفال الأدلة (Directory Handles):** على أنظمة POSIX، يمكن فتح واصف المجلد الأب واستدعاء `fsync` عليه. على Windows، يُرجع استدعاء `FlushFileBuffers` على مقبض مجلد خطأ `ERROR_ACCESS_DENIED`. يضمن NTFS سلامة المجلدات عبر تدوين المعاملات في `$LogFile` داخلياً عند إفراغ واصف الملف المنشأ.
  3. **إجراءات الأمان الإلزامية للملفات على Windows:**
     - عند إنشاء ملف جديد (`license_audit.log` أو ملفات اليومية المؤقتة): يجب فتح الملف بوضع الكتابة وتطبيق `os.fsync()` فور إنشائه لضمان تثبيت قيد الـ `$MFT` في دفتر أستاذ النظام.
     - عمليات الاستبدال الذرية للملفات المؤقتة تُنفذ باستخدام `os.replace` التي تستدعي داخلياً `MoveFileExW` مع علم `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`.

## 6. مصفوفة الاختبارات النظرية لحالات الانقطاع والتزامن والتلاعب (Theoretical Test Matrix)

توضح هذه المصفوفة حالات الاختبار الإلزامية التي ستُبنى برمجياً في اختبارات المهمة 3.4 للتحقق من كفاءة التصميم ومنع أي ثغرات:

| معرف الاختبار | السيناريو وظروف التشغيل | شروط الاكتشاف (Detection Criteria) | السلوك المتوقع للتعافي (Expected Recovery) | هل يُفرض قفل التصدير (Export Gate Lock)؟ |
| :--- | :--- | :--- | :--- | :---: |
| **TC-AUD-01** | التشغيل العادي المتتالي (Normal Flush) | `file_flushed = 0` و الملف ينتهي عند $N-1$ | إلحاق السطر $N$ بالملف وتطبيق `fsync` وتحديث `file_flushed = 1`. | ❌ لا (بوابة التصدير مفتوحة) |
| **TC-AUD-02** | انقطاع بعد كتابة السطر و fsync وقبل تحديث DB | `file_flushed = 0` والسطر $N$ موجود ومكتمل ومطابق 100% بالملف | اكتشاف التطابق التام، عدم تكرار الكتابة، وتحديث DB إلى `file_flushed = 1`. | ❌ لا (استعادة تلقائية ناجحة) |
| **TC-AUD-03** | انقطاع أثناء كتابة السطر وبايتات متبقية تطابق البادئة | `file_flushed = 0` والبايتات المشوهة $B_{\text{tail}}$ تمثل بادئة مطابقة لـ $B_{\text{expected}}$ | اقتطاع البايتات المشوهة إلى إزاحة $N-1$، إعادة كتابة السطر كاملاً، `fsync`، وتحديث DB. | ❌ لا (تعافي آمن مثبت رياضياً) |
| **TC-AUD-04** | انقطاع وبايتات متبقية بنهاية الملف لا تطابق البادئة | `file_flushed = 0` والبايتات $B_{\text{tail}}$ لا تطابق بداية $B_{\text{expected}}$ | حظر الاقتطاع، رمي `AuditIntegrityException` فوراً، تسجيل تحذير أمني. | ✅ **نعم (Hard Lock إلزامي)** |
| **TC-AUD-05** | بايتات مشوهة بنهاية الملف مع عدم وجود أي حدث معلق في DB | `outbox` لا يحوي أي حدث معلق و الملف ينتهي ببايتات غير صالحة | حظر الاقتطاع، إعلان تلاعب/تلف وسيط تخزين، رمي `AuditIntegrityException`. | ✅ **نعم (Hard Lock إلزامي)** |
| **TC-AUD-06** | تلاعب بتعديل نص أو حالة ترخيص في سطر تاريخي ($k < N$) | إعادة حساب Hash السطر $k$ يعطي قيمة تختلف عن `entry_hash` المسجل | اكتشاف كسر السلسلة، حظر الإصلاح التلقائي، رمي `AuditIntegrityException`. | ✅ **نعم (Hard Lock إلزامي)** |
| **TC-AUD-07** | تلاعب بحذف سطر تاريخي من منتصف الملف | فحص السلسلة يكتشف فجوة في أرقام `seq` وعدم مطابقة `previous_hash` | حظر ملء الفجوة آلياً، رمي `AuditIntegrityException`. | ✅ **نعم (Hard Lock إلزامي)** |
| **TC-AUD-08** | حقن سطر إضافي غير مصرح به في نهاية الملف | سطر موجود في الملف برقم $N$ غير مسجل إطلاقاً في `audit_events_outbox` | اكتشاف سطر دخيل من خارج SQLite، رمي `AuditIntegrityException`. | ✅ **نعم (Hard Lock إلزامي)** |
| **TC-AUD-09** | تزامن عمليتين تحاولان تفريغ السجل لنفس القناة في نفس اللحظة | العملية الأولى تحجز قفل `.audit_lock` بينما تحاول العملية الثانية الحجز | العملية الثانية تنتظر أو تفشل في حجز القفل الإجرائي؛ وتكتب العمليات بالتتابع التسلسلي الدقيق. | ❌ لا (تنظيم تزامن ناجح) |
| **TC-AUD-10** | تكرار طلب العملية نفسها بنفس مفتاح الحتمية (Idempotency) | محاولة إدراج حدث تدقيق بـ `idempotency_key` مكرر في نفس القناة | التقاط قيد الفرادة في SQLite، إعادة نتيجة القيد القائم دون زيادة `seq` ودون تكرار السطر. | ❌ لا (حتمية تامة) |

## 7. سياسة حذف الأصول والفصل الصارم للسجلات

### 7.1. مصفوفة المستويات الأربعة لإدارة الأصول:
```
1. Disable           ──► تعيين is_active = 0 (منع الاستخدام الجديد، بقاء الملفات والمشاريع القائمة)
2. Archive           ──► إخفاء من مكتبة الاختيار وحذف كاش proxies (بقاء الملف الأصلي وأدلة الترخيص)
3. Remove Association──► فك ارتباط الأصل بمشهد أو شخصية (لا يمس الملف الأصلي مطلقاً)
4. Permanent Purge   ──► حذف فيزيائي للأصل (مشروط بعدم وجود أي ارتباط نشط في DB، ومسجل في Audit)
```

- **الحصانة الدائمة:** أدلة التراخيص المادية في `media_vault/licenses/proofs/` وسجلات التدقيق في `audit/` **محظورة الحذف نهائياً (Permanent Retention)** حتى بعد الحذف الفيزيائي للأصل.

### 7.2. الفصل الصارم لمنظومة السجلات:
1. **سجلات التطبيق التشخيصية (`logs/studio.log`):** تتبع أخطاء الكود، وتخضع للتدوير اليومي وتحديد الحجم الأقصى (Log Rotation).
2. **سجل العمليات التشغيلية (`channels/<id>/audit/operations.log`):** تتبع أحداث القناة والمصالحة، إلحاقي ومحفوظ لفترات طويلة.
3. **سجل تدقيق التراخيص القانوني (`channels/<id>/audit/license_audit.log`):** توثيق السند القانوني والقرارات المحمية بـ Hash Chaining؛ **محظور التدوير أو الحذف نهائياً**.

## 9. التوافق العكسي وحالة الملفات الحالية (Zero-Touch Assurance)

1. **المجلدات الحالية على القرص:**
   المجلدات الستة الاختبارية الفارغة الموجودة في `channels/` تظل كما هي؛ لا تتطلب أي نقل أو حذف يدوي، وستقوم دالة التهيئة المحدثة لاحقاً بإنشاء أي مجلد فرعي ناقص تلقائياً وبأمان تام.
2. **الكود التطبيقي الحالي:**
   لم يتم إجراء أي تعديل على كود التطبيق في هذه الجولة، التزاماً بالقيود الصارمة.
3. **سلامة الاختبارات:**
   كافة الاختبارات الـ 39 ما زالت سليمة ومجتازة بنسبة 100%.
